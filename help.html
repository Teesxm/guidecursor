GuideCursor is AI-guided pointer support for people with low vision or blindness using macOS. A user says or types a goal, the system identifies and verifies the next relevant control, and GuideCursor guides the pointer there while the user makes every click.

Not currently. GuideCursor is focused on visual access on macOS. Hearing-focused assistance, motor-focused assistance and Windows are not part of the current release path.

The current MVP supports one end-to-end journey: attaching a CV to an email in Apple Mail, including the prepared file-selection window. Safari downloads and menu commands are only possible future tasks once the core journey is proven reliable.

GuideCursor uses a high-contrast outline around the verified target, an arrow from the pointer toward it and optional Zoom on the target. The user stays in the normal application and performs the click.

The same verified target is presented non-visually: the target name is announced through macOS accessibility mechanisms and short non-speech sounds convey direction and distance. This is designed to coexist with VoiceOver rather than compete with it.

No. The current product principle is explicit: GuideCursor never clicks, types, selects a file or confirms an action for the user. It solves finding and reaching the control, not completing the action autonomously.

It first reads the active window through the macOS Accessibility API. When controls are unlabelled, on-device screen recognition can add lower-confidence candidates from the visible pixels.

The architecture is designed to prevent that. The model receives a numbered text list of observed candidates and must answer with a candidate number, alternatives, confidence and next step. Anything outside the list is rejected, and the chosen element is re-checked in the live window before guidance.

GuideCursor is local by default. A local model served through Ollama is compared against an opt-in cloud model on the same accuracy and response-time tasks. Cloud processing receives only the text candidate list, never screenshots.

Not yet. The current course MVP is a browser simulation of the core Mail journey. The intended product is a native macOS application using the Accessibility API, local processing and real-pointer guidance, but that native implementation remains future work. See macOS product path.

No. Screenshots remain on device. If a user opts into cloud inference, only the text list of candidates is sent to the model.

macOS Accessibility permission allows the app to inspect roles, labels, states and positions in other applications. Because this is powerful access, GuideCursor uses explicit disclosure, local processing by default and a constrained target-verification model.

Intended-user testing is planned but has not yet been completed. A follow-up pilot would recruit people with low vision or blindness and measure task success, wrong controls, time on task, NASA-TLX workload, perceived control, target accuracy, clarifications and stops.

GuideCursor should improve or preserve task success while reducing errors or search time, without making users feel less in control.

The proposed model is an annual per-user workplace licence, potentially funded by an employer or relevant accessibility-support route such as UWV. Commercial viability and willingness to pay have not yet been validated.

No. A follow-up pilot would need to test willingness to pay among employers and funding bodies, then compare any licence price with development, support and maintenance costs before a sustainable pricing model is set.
