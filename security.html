02 · INTENDED ARCHITECTURE

Observe only enough to guide.

The product goal is to minimize how much context GuideCursor needs, keep interpretation close to the device where practical, and preserve a clear boundary between guidance and the user’s final action.

01Perceive

Read the active interface

Use only the permission and context needed for the active guidance task rather than treating the entire desktop as permanently available.

02Interpret

Understand the target

Prefer on-device interpretation for UI state and target geometry where the capability can reasonably run locally.

03Guide

Return assistance

Produce directions, highlighting, captions or target assistance without silently taking over unrelated controls.

04Discard

Minimize retention

Transient screen context should not become a permanent history by default. Retention should be explicit, limited and understandable.

Concept requirement, not current implementation. The separate desktop application still needs engineering, threat modelling, privacy review and validation before these principles can be treated as delivered security properties.
03 · PERMISSIONS

Powerful permissions need obvious controls.

A desktop assistant may require sensitive operating-system permissions. GuideCursor’s intended model is progressive permission, visible active state and an immediate way to pause.

Ask late. Explain clearly.

GuideCursor should not request every permission during installation simply because it may use them someday. The product should explain why a permission is needed at the moment it becomes relevant.

1
Least privilegeRequest the narrowest access that can complete the selected feature.
2
Visible active stateMake it obvious when screen understanding, microphone input or guidance is active.
3
Easy revocationUsers should be able to pause the assistant and return to system permission settings without hunting through menus.

04 · PRODUCT REQUIREMENTS

Security principles we would build toward.

These are design requirements for the future application, not certifications.

01

Least access by default

Permissions should be scoped to the active function and requested only when the user invokes a feature that needs them.

02

Local-first processing

Keep interface understanding on device where practical so routine guidance does not automatically require transmitting screen content.

03

Explicit cloud boundary

If cloud processing is introduced, make it an understandable product state with a clear purpose rather than an invisible implementation detail.

04

No hidden autonomy

GuideCursor should not silently perform unrelated clicks or expand its scope beyond the assistance the user requested.

05

Minimize sensitive logs

Operational logs should avoid unnecessary screen content, typed text and other information that is not needed to diagnose the service.

06

Trusted software delivery

A production release should use platform-standard signing, update integrity checks and a documented release process before real installers are distributed.

What GuideCursor cannot claim yet.
