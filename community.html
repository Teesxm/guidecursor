01 · WHY COMMUNITY

Accessibility software can become stronger when users and developers can extend it.

GuideCursor follows a principle already visible in mature accessibility software: a core product can stay focused while extensions address application-specific or user-specific needs.

PRECEDENT

NVDA shows the value of an add-on ecosystem.

NVDA allows community developers and external organisations to build add-ons that add or change features, improve support for particular applications and extend assistive functionality. GuideCursor uses this as inspiration for a future modular contribution model.

GUIDECURSOR PRINCIPLE

Extend the role, not the user's loss of control.

A future extension may know more about a particular application or accessibility barrier, but it should still operate inside GuideCursor's core rules.

User makes the actionNo extension should silently click, choose or confirm on the user's behalf.
Targets stay verifiedGuidance should point to a control that exists in the current interface state.
Scope stays visibleUsers should know which extension is active and what it is allowed to read or guide.
02 · MODULAR ARCHITECTURE

The community layer sits on top of the same trusted core.

GuideCursor does not need a separate product for every application. The long-term idea is a common guidance engine with modules that understand additional interfaces and tasks.

01

Core GuideCursor

The platform owns the interaction rules and accessibility behavior that should remain consistent across every extension.

  • Intent interpretation
  • Interface re-reading
  • Target verification
  • Pointer and audio guidance
  • User-controlled final action
02

Extension modules

Modules could add application knowledge, task definitions, labels or accessibility-specific guidance without replacing the core engine.

  • Application mappings
  • Task-specific logic
  • Barrier-specific guidance
  • Optional local resources
03

Community ecosystem

Developers, accessibility specialists and users could help GuideCursor cover workflows that matter to smaller communities.

  • Discover extensions
  • Version compatibility
  • Contribution documentation
  • Feedback and maintenance

04 · CONTRIBUTION MODEL

Community-built should not mean uncontrolled.

The exact contribution system is still future work. A sensible model would combine open contribution with compatibility checks, clear permissions and visible user trust signals.

01

Build

A contributor creates a module for a specific application, workflow or accessibility need.

05 · TRUST MODEL

The platform can expand without changing who stays in control.

Whatever the extension ecosystem becomes, the user-control principle should stay fixed across the platform.

No silent actions

Extensions can identify, explain and guide. The user still performs the click, selection or confirmation.

USER AGENCY

Permission-scoped modules

Extensions should request only the application or interface access they genuinely need.

MINIMUM ACCESS

Visible compatibility

Users should be able to see supported app versions, maintainer information and whether a module has been tested recently.

TRANSPARENCY

Core guidance stays consistent

Community modules should plug into one shared interaction model rather than inventing incompatible control behavior.

CONSISTENCY

Prove one workflow.
Then let the platform grow.
