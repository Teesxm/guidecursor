1. Ability-based design

GuideCursor follows ability-based design: the system should adapt to what the user can do rather than requiring the user to adapt to one fixed interaction style. In this MVP, that means the underlying target-identification mechanism stays the same while the output changes depending on the user’s remaining vision.

The product does not replace the normal application. The user remains in Mail, Finder or another supported macOS app and retains control of every click.

2. Low-vision guidance

Users with low vision receive visual guidance toward a verified target. The current concept uses a high-contrast outline around the target, an arrow from the pointer toward it and optional Zoom around the target.

  • High-contrast target outline.
  • Pointer-to-target directional arrow.
  • Optional integration with macOS Zoom.
  • Confirmation that the pointer is on the intended control before the user clicks.

This is designed to reduce the need to pan around a magnified interface searching for a control whose location is unknown.

3. Blind-user guidance

Users with little or no usable vision receive non-visual guidance to the same verified target. GuideCursor names the target and uses short non-speech sounds to communicate direction and distance.

  • Spoken target name through the macOS accessibility announcement mechanism.
  • Short sounds for direction and distance.
  • Confirmation when the pointer reaches the target.
  • Keyboard-accessible GuideCursor controls.

The aim is to add direct spatial guidance to the normal workflow rather than forcing the user to step through unrelated controls to discover where the requested one is.

4. Working with VoiceOver and Zoom

GuideCursor is not intended to replace Apple’s built-in accessibility tools. It is designed to work alongside them. Visual guidance can make use of Zoom, while spoken messages should use the macOS announcement mechanism so VoiceOver can present them as speech or braille.

Avoid two competing voices. Direction is therefore proposed as short non-speech sounds rather than a second stream of continuous spoken instructions.

5. Website accessibility

The website itself is a concept presentation rather than the native assistive product. It includes keyboard-accessible navigation and controls, readable text labels, responsive layouts and reduced-motion handling for users who prefer less animation.

The interactive demo is illustrative. Browser speech and simulated interface states do not prove the native macOS application’s accessibility.

6. Co-design and testing

The MVP plan involves intended users from the start. A first round with 5–8 participants with low vision or blindness is intended to shape wording, sounds, highlight style and confirmation points. A second round compares participants’ usual tools with GuideCursor on the selected tasks.

Measures include task success, wrong controls, time on task, NASA-TLX workload and perceived control. GuideCursor should only be developed further if it improves or preserves task success without making users feel less in control.

7. Known limitations

This is a student MVP and has not been independently certified against a specific accessibility standard. The native prototype still needs formal testing with intended users, assistive-technology compatibility testing and broader reliability work.

Support for hearing impairment, motor impairment, Windows and broad application coverage is outside the first version and should not be inferred from earlier concept materials.
