1. Ability-based design

GuideCursor follows ability-based design: the system adapts to what the user can do rather than requiring the user to adopt one fixed interaction style. The target-identification mechanism stays the same while guidance output can shift from highly visual to fully non-visual.

The product does not replace the normal application. The user remains in Mail, Finder or another supported macOS app and retains control of every click.

2. Low-vision guidance

Users with low vision receive visual guidance toward a verified target. GuideCursor uses a high-contrast outline around the target, an arrow from the pointer toward it and optional Zoom around the target.

  • High-contrast target outline.
  • Pointer-to-target directional arrow.
  • Optional integration with macOS Zoom.
  • Confirmation that the pointer is on the intended control before the user clicks.

The goal is to reduce the amount of visual searching required when magnification limits how much of the interface is visible at once.

3. Blind-user guidance

Users with little or no usable vision receive non-visual guidance to the same verified target. GuideCursor names the target and uses short non-speech sounds to communicate direction and distance.

  • Spoken target name through the macOS accessibility announcement mechanism.
  • Short sounds for direction and distance.
  • Confirmation when the pointer reaches the target.
  • Keyboard-accessible GuideCursor controls.

The aim is to add direct spatial guidance to the normal workflow without replacing VoiceOver or forcing the user to discover the target by stepping through unrelated controls.

4. Working with VoiceOver and Zoom

GuideCursor is not intended to replace Apple’s built-in accessibility tools. It is designed to work alongside them. Visual guidance can make use of Zoom, while spoken messages should use the macOS announcement mechanism so VoiceOver can present them as speech or braille.

Avoid two competing voices. Direction is therefore proposed as short non-speech sounds rather than a second stream of continuous spoken instructions.

5. Website accessibility

The website includes keyboard-accessible navigation and controls, readable text labels, responsive layouts and reduced-motion handling for users who prefer less animation.

The interactive preview is illustrative. Native accessibility quality is validated separately in the macOS application.

6. Co-design and testing

GuideCursor is designed around iterative validation with people with low vision or blindness. Wording, sounds, highlight style and confirmation points are evaluated against real task performance and perceived control.

Validation focuses on task success, wrong controls, time on task, workload and perceived control. New capabilities should improve or preserve successful task completion without making users feel less in control.

7. Known limitations

GuideCursor is still in pre-release development and has not been independently certified against a specific accessibility standard. The native app continues to undergo intended-user testing, assistive-technology compatibility testing and broader reliability work.

Current product support is focused on visual access on macOS. Hearing-focused assistance, motor-focused assistance, Windows and broad application coverage are not yet supported.
