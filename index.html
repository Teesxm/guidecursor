01 · THE BARRIER

The control exists.
Finding it is the problem.

GuideCursor focuses on one barrier: getting from a user’s goal to the specific control they need in mainstream macOS software. Existing accessibility tools remain essential, but the user often still has to search through the interface themselves.

LOW VISIONSearch while magnified.

Zoom and Hover Text enlarge what is visible, but magnification shows less of the interface at once. The user can still spend time panning to find the right control.

GuideCursor adds: a verified target, high-contrast outline and arrow. The planned native product can also integrate macOS Zoom; the browser MVP does not simulate that part.
BLINDNESSStep through many controls.

VoiceOver reads interface elements and enables keyboard navigation, but reaching one particular control can require moving through many others.

GuideCursor adds: the target name plus short directional and distance sounds, while VoiceOver remains available.
UNLABELLED UINot every app exposes enough.

GuideCursor first uses macOS accessibility metadata. When a control is not labelled, on-device screen recognition can add lower-confidence candidates from visible pixels.

GuideCursor adds: verification before guidance, rather than letting the AI invent a control.
02 · TWO GUIDANCE MODES

One mechanism.
Different output.

GuideCursor adapts to the user’s remaining vision instead of forcing one accessibility workflow. The product is focused on visual access, with guidance that can be tuned from highly visual to fully non-visual output.

LOW VISION

Visual guidance

The user stays in the normal application while GuideCursor makes the needed control easier to locate and reach.

High-contrast outline around the verified targetArrow from the pointer toward the targetPlanned macOS Zoom integration for the native productConfirmation before the user clicks
BLIND / LITTLE USABLE VISION

Audio guidance

The same verified target can be communicated without depending on visual cues.

Target name through the macOS accessibility announcement mechanismShort non-speech sounds for direction and distanceConfirmation when the pointer reaches the controlVoiceOver-compatible settings and keyboard operation
User control is non-negotiable. GuideCursor never clicks, types, chooses a file or confirms an action on the user’s behalf. It solves finding and reaching the control; the user performs the action.

04 · HOW IT WORKS

AI interprets.
The interface verifies.

The language model is not allowed to freely point at the screen. GuideCursor separates understanding the user’s request from deciding where to guide, so every target must be grounded in controls that exist in the current window.

1READ

Inspect the active window

With permission, the macOS Accessibility API exposes each control’s role, label, state and position.

2FILL GAPS

Add visual candidates

If controls are unlabelled, on-device screen recognition can add lower-confidence candidates from a screenshot.

3INTERPRET

Map goal to candidates

The model receives the goal plus a numbered text list and returns a best match, alternatives, confidence and next step.

4VERIFY

Check the live control

The chosen element must still exist, be visible, enabled and clickable. Anything outside the list is rejected.

5GUIDE

Run a local pointer loop

Once verified, pointer-to-target guidance updates locally without asking the AI on every movement.

05 · PLANNED NATIVE ARCHITECTURE

Work screens should stay on the Mac.

The final product is designed to process screen context locally by default, with cloud inference opt-in. The current course MVP is a browser simulation and does not yet implement this native processing pipeline.

PLANNED DEFAULT

On-device inference

In the intended native macOS product, screen context stays on the Mac by default. Local models could be served through Ollama; performance and accuracy still need to be tested on supported Macs.

✓ Screenshot stays on device✓ Candidate list + model can run locally✓ Offline-capable△ Must prove response time and target accuracy
PLANNED OPT-IN

Cloud model

A cloud model may offer stronger capability, but it would require an internet connection, introduce usage cost and send the text candidate list to a third party.

Opt-in onlyReceives candidate text, never screenshotsCompared on the same target-accuracy and response-time tasksDefault chosen from evidence, not assumption
06 · FOCUSED ROLLOUT

Start focused.
Expand where reliability holds.

GuideCursor starts with a small number of deeply supported workflows. Reliability matters more than claiming universal application support before it has been proven.

Initial workflow · Mail

Attach a specific file to an email while GuideCursor guides the user through both Mail and the file-selection window.

1Find AttachInterpret “attach my CV” and guide to Mail’s Attach control.
2Choose the intended fileIf several files match, ask the user which one they mean instead of guessing.
3Find OpenRe-read the new window, verify Open and guide the pointer there.

Expansion path

Broader workflows are added only when the same target-verification standard holds.

Possible future taskExplore downloading a file in Safari after the Mail journey proves reliable.

07 · VALIDATION

Measure what matters:
success, effort and control.

GuideCursor should earn trust through measurable outcomes: successful task completion, fewer wrong targets, less time spent searching and no loss of user control.

Planned user-centred validation

Guidance language, sounds, highlights and confirmation points will be evaluated with people with low vision or blindness. The current course MVP has not yet completed this intended-user testing.

08 · COMMUNITY EXTENSIONS

One core guide.
A platform that can grow.

The current GuideCursor MVP stays focused on a reliable Mail journey. Longer term, the same verified guidance engine could support modular extensions for different applications, barriers and accessibility needs.

FUTURE PLATFORM DIRECTION

Community-built modules can expand what GuideCursor understands.

Accessibility software already shows the value of community extensibility. NVDA supports add-ons created by its community and external developers for application support and additional functionality. GuideCursor follows a similar principle: keep the core interaction model consistent, then let future extensions add specialised knowledge around it.

10 · EVIDENCE-LED DESIGN

Accessibility decisions
should be evidence-led.

GuideCursor draws on ability-based design, low-vision and non-visual navigation research, screen recognition and established usability principles.

ABILITY-BASED DESIGN

Wobbrock et al. (2011)

Technology should adapt to what people can do rather than requiring them to adapt to a fixed interface.
